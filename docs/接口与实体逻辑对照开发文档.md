## 2. 原始接口与返回：两个后端并非同一协议

### 2.1 A 的 OpenClaw / AI 接口

全部通过 aiohttp 发送 JSON POST，默认超时 15 秒；返回为普通 JSON。这里的成功结构来自源码预期，不能当作本次官方成功返回。

| 操作 | POST 完整接口 | 请求与鉴权 | 响应处理及验证状态 |
|---|---|---|---|
| 登录 | `https://api-passport-bj.ninebot.com/v3/openClaw/user/login` | body：`username,password`；headers：`clientId=open_claw_client,timestamp=毫秒`；代码未生成 `sign` | 期待 `data.access_token`、可选 `refresh_token/accessTokenValidity`。实测 HTTP 200、业务 `resultCode=90051,resultDesc="sign is null"`，无 token；本次没有复现 404 |
| 车辆列表 | `https://cn-cbu-gateway.ninebot.com/app-api/inner/device/ai/get-device-list` | body：`access_token,lang` | 期待 `data` 为 list，保留其中 dict；登录失败后未取得有效 token，未验证成功调用 |
| 单车状态 | `https://cn-cbu-gateway.ninebot.com/app-api/inner/device/ai/get-device-dynamic-info` | body：`access_token,sn` | 期待 `data` 为 dict，返回给 coordinator；本次未验证成功调用 |

实测登录原文：

```json
{"resultCode":"90051","resultDesc":"sign is null"}
```

`_result_ok` 读取 `resultCode`，否则 `code`；缺省 code 也接受，0/1 视为成功。登录以 token 存在为首要判断；业务列表/状态还检查 data 类型。虽然保存了 refresh token，`async_ensure_token` 的刷新路径实际重新调用账号密码登录，refresh-token 调用尚为 TODO。

结论限于“现有请求缺少当前服务要求的 sign，无法取到 token”。没有证据据此断定所有旧 API 永久关闭，也没有验证用户 API key 的新公开契约。

### 2.2 B 的 App 协议与 CLI 边界

HA Python → `python -m ninecli --config <隔离或HA会话目录> <command> --json` → Python shim 执行捆绑 Go 二进制 → 官方 HTTPS → 解密提取 data → stdout JSON → Python 归一化。B 的 Python 集成本身没有实现 HTTP 签名/AES/RSA。

| 操作/CLI | 官方接口 | 原始参数要点 | 本次证据 |
|---|---|---|---|
| Passport 登录 `login` | `https://api-passport-bj.ninebot.com/v6/user/login` | body 有 `areaCode="86",device="ANDROID",username,password`；App clientId、timestamp、sign | 静态与离线假凭据请求证据；**未重新发送真实密码登录** |
| 业务登录 | `https://api-jhcx-v6-bj.ninebot.com/user/user/login` | Passport 会话用于业务登录，业务 uid 存为 `business_uid` | 静态调用链；未新登录 |
| `vehicles` | `https://ebike.ninebot.com/vehicle/binding/my-vehicle` 和 `https://steeldust.ninebot.com/vehicle/binding/my-vehicle` | App 公共参数及业务类型；CLI 合并来源 | 实测成功，两车 profile 包含在合并列表中；不把合并列表误称某一个 host 的原始数组 |
| `status <SN>` | `https://ebike.ninebot.com/vehicle/vehicle/desktop-component` | 车辆参数名是 `sn_str` | 两车实测成功 |
| `battery <SN>` | `https://ebike.ninebot.com/v6/vehicle/battery-info` | `wnumber` | 两车实测成功 |
| `travel <SN> --month YYYYMM` | `https://cn-cbu-gateway.ninebot.com/app-api/travel/v6/travel-list2` | `wnumber,month,rnVersion,vehicle_type,page,current_version` | 两车当月实测成功；此前还核验了 MzMIX 的上月回退结果 |
| `bell/buck/engine-stop/engine-start` | 本文不提供未经实测的控制 HTTP 契约 | Python 命令路径已核对，见实体表 | **未执行控制、未验证效果或控制返回** |

Passport `sign` 的静态链路：合并公共参数与 body，并加入 `clientKey`、URL path、timestamp，键排序，拼接 `key=value&...`，计算 SHA-256 小写十六进制。这里的 App clientKey 与用户申请的 API key 不是同一概念。相关常量不写入报告。离线生成的登录请求有 `clientId=vehicle_app_prod`、64 字符 sign、Android 与 app version headers；尚未用独立重写实现验证完整登录。

业务请求内部包含 `access_token` 和语言/客户端/设备参数，业务身份通过 `Uid` header 传递；headers 还包含 `Device-Id,Request-Id,Service-Time,Business-Type,Client-Ver,Platform,Regionx,Need_decrypt,Ninebot-Version`。请求包装为：

```json
{"d":"<AES密文base64>","h":"<包装明文MD5>","k":"<RSA加密请求密钥base64>","p":"101","t":"0"}
```

HTTP 返回包装为：

```json
{"v":101,"s":"<opaque字段>","r":"<加密响应base64>"}
```

二进制中可确认 AES-CBC/PKCS7、RSA PKCS#1 v1.5、派生密钥与业务码检查路径，但尚未重写完整 DeriveKey/包装算法。不要将 `s` 未经验证解释为 token 或签名。**下文“原始字段”指 CLI 解密并提取后的业务 data，未经过 HA Python 的 normalize；不是上述 HTTP 密文，也不是完整解密业务 envelope。** HTTP 和 data 的对应证据均保存在补充目录。

CLI 命令由一个 asyncio lock 串行执行，30 秒超时后 kill 并 wait。通用 `server code=` 错误被分到认证异常的逻辑过宽，已离线复现；服务临时故障不应都触发重新认证。

## 3. 原始字段到标准状态的映射

### 3.1 单车实时状态

| 含义 | A 的源码字段 → coordinator | B 的原始字段 → coordinator | FMIX / MzMIX 实测 data | 合并要求 |
|---|---|---|---|---|
| 电量 | `battery`，否则 `dumpEnergy` → int `battery` | `dump_energy` → int `battery` | `"93"` / `"79"` | snake_case 显式适配；不要填 0 代替缺失 |
| 续航 | `estimateMileage`，否则 `mileage` → `estimateMileage`，先保留原类型 | `precise_estimate_mileage` → float `endurance` | 104.7 / 98.5；普通估计另为 86.4 / 88.7，AI 估计另为 0 / 28.8 | 三种算法分别保留；选择 precise 作为默认时须记录来源，不能默认为旧普通续航同一口径 |
| 充电 | `chargingState` → int | `charging` → 原值 `charging` | 0 / 0 | 标准 bool 校验 0/1；现 B 未将字符串转换为 int |
| 主电源 | `pwr` → int `pwr` | `pwr` → 原值 `power` | 1 / 1 | 显式规范化类型 |
| 锁 | `status`，否则 `powerStatus` → int `status`，**0锁/1开** | `loc.lock` → int `lock`，**1锁/0开**；loc 非 dict 才尝试 `lock_status` | `loc.lock=1` / 1 | 标准态采用 `locked: bool\|None`；A 兼容层 `status=0 if locked else 1`，未知仍 None |
| 坐标 | 仅保留 dict `locationInfo`；位置 sensor 使用其中地址文本 | `loc.lat/lon` → float，均可解析才生成 `location` | 两车有坐标；文档及夹具已脱敏 | 新增 tracker；校验有限值、范围和坐标系，不能用接收时间伪造车辆定位时间 |
| 充电剩余 | `remainChargeTime` 原值 | 原始 `remain_charge_time` **当前被丢弃** | `""` / `""`，另 `remain_charge_timestamp=0` | 可适配到旧文本实体；空值未知，时间戳 0 不造预计完成时间 |
| GSM | `gsm` → int | 本次 status 无对应字段 | 无 | 旧 CSQ/RSSI 保留兼容身份，但 App 来源不能虚构信号 |
| GSM 上报时间 | `gsmTime` → int，timestamp 实体按秒解释 | 本次 status 无对应字段 | 无 | 接收时间与设备报告时间分开；旧实体未知 |
| 地址文本 | `locationInfo.locationDesc` | 本次 status 无地址字段 | 无 | 经纬度不能直接冒充地址；逆地理编码属于另一个可选功能 |

A 的 `_first_present` 只判断非 None；空字符串也会阻止备选字段。A int 解析接受 bool/int/整数字符串，不接受 float；B int 解析还将 float 截断。B float 解析接受数值/字符串；当前两侧的浮点解析都缺少统一 `isfinite` 检查。合并后应测试空字符串、NaN/Infinity、异常枚举，不能只接受示例中的正常数字。

### 3.2 列表、行程和 BMS

| 来源 | B 当前归一化 | 数据用途与遗漏 |
|---|---|---|
| vehicles | `wnumber` 否则 `sn` 作为非空字符串 SN；name 取 `device_name/ble_name/SN`；model 取 `vehicle_name_en/vehicle_name/SN` 并附 `vehicle_type`；图片优先 `v6_light_img_url` 否则 `img_url`；保留 raw | 生成 DeviceInfo、绑定实体和 tracker 图片。A metadata 则期待 `deviceName/name/img/model/productName`，也要显式适配 |
| travel 当月 | `total_mileages→month_mileage`、`ec→month_energy`，均 float；`used_electricity→month_used_electricity` 可选 | 本次当月 `total_mileages="0.0",ec=0,list=null`；0 是有效月合计，null list 不等于故障 |
| travel 最近一次 | 将 `list[0]` 当最后一条，`mileages→last_mileage,ec→last_energy,used_electricity→last_used_electricity`；整条保留 `last_ride` | 没有验证列表排序与分页能覆盖“最后一条”；无记录时这些 last 字段为 None |
| battery | 支持顶层或 dict `data` 包装；只取 `battery_list[0]` 的 `bms_volt→bms_voltage,bat_temp→batt_temp,bms_cycle→bms_cycles,score→bms_score`；顶层 `charging_power` float | 无电池索引/SN identity；多电池没有展开；不检查 `have_bms_cycle_support` |

实测 battery：FMIX 的第一块 `bms_volt="75.3",bat_temp="26",bms_cycle="100",electricity="93",score=0`；MzMIX 为 `"75.6","25","100","79",0`。两车均 `have_bms_cycle_support=false`、`battery_count="0"`，却各有一条 battery_list。B 当前仍生成循环次数 100。**100 只能确认为原始字段值，不能确认为真实循环次数；score=0 也不能解释成健康度 0%。** 电池主控 `battery_main.electricity` 分别 100/93，与车辆电量不同，B 没有生成这个字段的实体。

未生成独立实体的字段还包括 AI/普通续航、barrel_lock_status、电池存在、智能服务到期、permissions、充电保护、充电时间戳、battery_count/type、各电池 electricity、battery_main、travel detail/duration/times/first_time。`charging_power`、`bms_score`、`used_electricity` 目前仅成为属性。字段出现在 JSON 中不代表已在 HA 暴露，也不代表含义和单位已验证。

## 4. 调度、缓存、创建与可用性

| 环节 | A：当前源码行为 | B：当前源码行为 | 建议 |
|---|---|---|---|
| coordinator 结构 | `{SN:{device,state}}` | `{devices:{SN:{info,state}}}` | provider 输出中立 profile/status/battery/travel；兼容 A 的实体取值层 |
| 状态周期 | coordinator tick 2 秒，仅查询到期车；默认 60 秒、解锁 3 秒、充电 30 秒，解锁优先；并发默认 3 | 默认 120 秒，现 HA 选项 30 秒；逐车串行；CLI 自身也串行 | 按车调度与限流；避免因 HA tick 更快而重复 CLI |
| 列表周期 | 默认 24 小时；某些错误触发强制列表刷新 | 每小时；未再返回的旧车仍被保留 | 失联/移除状态显式记录，避免永久留存旧可用态 |
| 详情周期 | 动态接口一次取得状态；能量只在成功取样后计算 | 每车 10 分钟：先行程再 BMS；失败仍登记详情查询时间，缺失字段保留旧值 | 分开成功时间和尝试时间，详情失效不影响实时状态；失败可退避重试 |
| 状态异常 | 使用缓存与失败计数；已有缓存时失败容忍上限不能可靠切为 unavailable，且实体未读取 state.available | 任一车状态连接异常使整个 coordinator UpdateFailed；所有车通常一起 unavailable | 按车、按数据组 last_success/TTL；鉴权失败与临时网络故障分开 |
| 缺字段 | 成功 normalize 通常含 None 字段；非到期车辆沿用缓存；`data_source=live` 可跨 tick 保留 | 普通更新先合并旧 state，再覆盖新 status；接口省略字段时可能永久保留旧值 | 区分 absent / null / 0，陈旧值带 freshness，不默默当实时 |
| 创建时机 | 每个平台 setup 遍历 coordinator.data 一次，没有后续发现监听 | 每个平台监听 coordinator，known_sns 防重复，动态增加新车；没有自动移除 | 动态增车；移除与 entity registry 迁移需设计 |
| 基础可用性 | 继承 CoordinatorEntity，主要依赖账号级 last_update_success；不判断该 SN 是否存在或 state.available | 账号级 last_update_success 且该车 payload 为 dict | 实体所属数据组有可用性；值未知不等于整车 unavailable |
| 图片/定位例外 | image 额外要求 URL；下载失败返回 None，但 available 不一定随下载失败变 false | tracker 额外要求 numeric latitude/longitude | 限定失败影响范围；坐标应更严格验证 |
| 主值更新 | 多数 property 每次从 coordinator state 读取 | sensor/binary 在 coordinator 通知时更新 `_attr_*`，属性函数同时运行 | 保持通知一致，避免修改 dict 后遗漏通知 |

B 的控制后 `async_request_device_status_refresh` 与普通周期更新不同：保留 month_/last_/BMS 字段，但用此次 status **替换**其他状态字段；visible state 比较忽略 raw，相同则不通知，也不更新 raw。应统一字段缺失策略和 freshness 更新。B 的 DeviceInfo 名称/型号在实体构造时赋值，profile 后续变化不自动重建该属性；A 则通过 property 动态读取。

### 4.1 身份与注册表

两者 domain 和安装目录均为 `ninebot`，DeviceInfo.identifier 都是 `(ninebot,SN)`，**不能作为两套同名集成同时安装验证**。设备相同不意味着实体 unique_id 相同。

- A 的 unique_id/object_id 为 `ninebot_<SN>_<key>` 小写；通常 entity_id 为 `<platform>.ninebot_<sn>_<key>`。其启动注册表清理/强制命名逻辑会删除不在预期列表中的条目，合并前必须去掉无条件清理策略。
- B 的 unique_id 为 `<SN>_<key>`（保留 SN 大小写），但源码直接设 entity_id 为 `ninebot.<sn>_<key>`；这是错误的实体域。当前 HA 可修正域，已有日志警告未来版本会拒绝。应由实际 platform 正常生成建议 object_id，保留现有 registry 身份。
- 表中的 key 是源码 key，不是实际实例完整 entity_id；用户重命名与同名冲突可使 entity_id 不符合默认格式。
- 迁移须同时考虑“原来用 A”的历史和“现 HA 用 B”的历史：匹配 config entry/platform/SN/功能语义，明确旧→新 unique_id，保留 entity_id、统计历史和用户设置。不能只按名称删除重建。

## 5. A 的全部实体逻辑表（33 类）

本节“来源”是 A **当前标准 state/device**及其旧原始字段契约；并非宣称旧动态接口本次返回成功。所有行默认遵循第 4 节 A 的基础可用性和创建规则。`DC` 为 device_class，`SC` 为 state_class，`—` 表示未设置。显示精度不等于计算精度。

### 5.1 sensor：24 类

### 5.3 A 的估算链必须单独保留

成功状态取样时：R→本地 M→计算 p→能量 snapshot→存储→sensor。参与累计的是 **A02 的 p，不是 A01 的 raw SOC**。单步能量检查使用原始高精度计算；返回能量 round 6、功率 round 3，sensor 显示 3 位。

- 首有效样本仅建立基线；时间差≤0 拒绝，p 无变化记 no_change，|Δp|>80 拒绝，|Δp|>40 且时间差<60秒拒绝，无效 p 拒绝。
- 0..100 内的有效 p 即便变化被拒绝，仍更新 last_battery_percent/last_sample_ts。`last_valid_battery_percent` 则只在实际积累时更新；两者含义不同。
- 日/月桶在 `async_build_energy_snapshot` 内按 HA 本地时间重置。无新成功查询时，午夜后的实体不会立即自动归零；跨边界的能量整步计入当前桶。
- 窗口历史至少保留 300 秒；功率除以配置窗口而非两个取样的实际间隔。30/60 秒云端更新产生离散阶跃，15 秒窗口可能放大成峰值；没有功率阈值验证。
- 存储使用 HA Store：`ninebot_<entry>_runtime`，schema 3、accumulation 2；A 的 token/列表是另一份 api_cache。B 的 CLI 会话目录另存 tokens/config/vehicles，不能混用格式。
- 已离线复现：云端剩余里程保持 50km，将 M 从 100 改 200，p 从 50% 到 25%，默认 N=1.44kWh 会被算成 0.36kWh 放电及 86400W 窗口峰值。接入 precise 续航或更换电池也可能触发类似口径跳变。

建议明确“估算”名称与 source；修改参数、切后端/续航算法、更换电池时建立新基线，不为该次变化累计；保留既有累计历史并记录版本。不要把官方行程 ec 与本地推算电量直接合并。

### 6.3 上月回退不能覆盖本月字段

源码 `async_get_device_travel`：取当月→若没有 last_ride，再取上月→若上月有 last_ride，**返回整份上月 normalized state**。这会同时覆盖 month_mileage/month_energy。

此次当月原始两车均 0km/0ec/list=null。先前实际封装测试，MzMIX 回退后返回 last_mileage=0.3、last_energy=5，却也返回 month_mileage=303.9、month_energy=7210；这后两项来自上月。不能把它们写作“十月已骑行303.9km”。本轮直接回放当月原始 data 未运行回退，因此输出 month 0、last None；两份结果的差异有明确来源。

修正要求：保存当月全部 month_*；上月仅补 last_* 与 ride_month/source_month；当月故障未知，不能借上月返回掩盖；当月有合法 0 合计，应保留 0。若继续跨更早月份搜索，另设页数/月数/请求预算并保留“未找到”的状态。

B 默认 query_month 来自 `datetime.now(UTC)`，A 的日/月桶按 HA 本地时区。上海时间每月1日00:00..07:59，UTC仍是上个月；“本月”云端查询与本地显示可能错月。应按业务指定时区确定 query_month，并测试跨月、跨年边界。

## 9. 建议开发结构与验收顺序

先实现只读 `AppProvider` 包装 ninecli，保持 Go 密钥/协议封装边界，不立即重写未完整验证的加密协议。provider 接口分 `list_vehicles/get_status/get_battery/get_travel`，输出带 `source,fetched_at,source_reported_at,query_month,capabilities` 的中立数据；时间不存在则 None。再以 adapter 保持 A 的实体结构，分离 per-device/per-group cache。旧 OpenProvider 留作可选来源，但只按真实错误报告，不推断“官方永久关闭”。

最小模型建议：

```text
VehicleProfile(sn, name, model, image_url, capabilities)
Status(battery_percent, locked, powered, charging,
       range_precise_km, range_estimated_km, range_ai_km,
       location, charge_remaining, source_reported_at)
BatteryInfo(batteries[], cycle_supported, charging_power, fetched_at)
TravelMonth(query_month, mileage, energy_raw, energy_unit, last_ride)
DataGroupFreshness(last_attempt, last_success, error, stale)
```

避免 provider 直接输出 A 的锁整数和 B 的锁整数：二者先解码为 locked bool，再由实体/兼容 adapter 编码。容量/标称电压/最大续航留在本地参数模型，不从 BMS 自动改写。

| 顺序 | 必须验证的场景 | 通过标准 |
|---|---|---|
| 1 | 原始 fixtures → profile/status/battery/travel；0、None、缺键、字符串、异常枚举、NaN | 与本文映射一致；未知不变成0/False；敏感字段不入日志/诊断 attrs |
| 2 | loc.lock 的0/1/None与旧status的0/1/None交叉 | A27/B12 on 都表示解锁；A28/B14 locked都表示上锁 |
| 3 | 当前月空、上月有行程、跨年、当前月故障、无历史 | month_*永远属于 query_month，last_*可来自其他月且标明 |
| 4 | support=false、缺battery_list、多块电池、更换电池 | 不虚报循环/健康度；电池identity明确；某块失败不影响其他数据组 |
| 5 | 单车超时、详情失败、removed vehicle、缓存过期 | 账号下另一车可更新；按组可用性与TTL；不永久展示旧值为实时 |
| 6 | 本地参数变更、续航算法变更、首次取样、跨日/月 | 不累计配置造成的虚假能量；自然日/月语义与显示重置明确 |
| 7 | A旧registry与B旧registry两种迁移 | 无启动时破坏性清理；保留entity_id、unique_id迁移映射、历史与用户配置 |
| 8 | 未来HA实体域与sensor统计检查 | 无ninebot错误实体域、无energy+measurement告警；统计口径明确 |
| 9 | 可选控制阶段 | 先修复并发锁缺失，再验证模拟回执/权限/超时/延迟任务生命周期；独立确认实机控制语义后再开启 |

本次通过的是源码计数、离线原始 data 回放和此前缺陷复现；迁移、部署、新 provider、控制与所有上述验收项尚未实现，不把文档完成当作合并完成。
